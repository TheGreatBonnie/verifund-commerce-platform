# Verifund Transaction Control Plane — Design

**Date:** 2026-10-27  
**Status:** Approved 2026-10-27  
**Scope:** Standalone transaction-control subsystem under `verifund-a2a/apps/`  
**Supersedes:** The payment/escrow/transaction-coordinator non-goals in
`docs/superpowers/specs/2026-10-21-marketmesh-a2a-commerce-design.md` when
`VERIFUND_MODE` is `fake` or `sandbox`.

## 1. Purpose

MarketMesh currently ends at order placement. This design adds the missing
commercial lifecycle: the buyer funds an award, the control plane holds the
funds, the seller submits shipment evidence through a scoped transaction token,
the control plane verifies the evidence, a reviewer releases the funds, PayPal
pays the seller, and the buyer receives a signed receipt.

The implementation is a fresh subsystem inside `verifund-a2a/`. It is not a
runtime dependency on `verifund-platform-backend` and does not import, call, or
reuse that backend. The control plane is the only authority for money and
transaction state. The buyer and seller agents are control-plane clients; a
registered Verifund A2A agent coordinates settlement conversations through the
buyer's authenticated settlement API. The existing CopilotKit orchestrator
invokes that agent and presents approval and status interactions in chat. The
console reaches settlement data only through the buyer.

`VERIFUND_MODE=off` is the default and preserves the current MarketMesh flow
exactly: discovery, negotiation, approval, order placement, and finalization
without payment or settlement.

## 2. Goals

- Implement the full lifecycle: award → Verifund agreement draft → buyer-agent
  and seller-agent review of the same hash → human funding approval → PayPal
  funding → held funds → seller evidence →
  verification → release/payout → receipt.
- Use real PayPal Sandbox Orders, Capture, Payouts, and webhooks, with polling
  as a fallback.
- Let sellers upload shipment/evidence directly with short-lived, scoped
  transaction tokens.
- Extend the existing MarketMesh console; do not create a second frontend.
- Add a separately discoverable Verifund A2A agent for agreement, transaction,
  evidence, funding, release, and receipt workflows.
- Make chat the primary settlement interaction surface using CopilotKit HITL
  cards and frontend tools; retain the Transaction Room as a synchronized
  transaction detail view.
- Keep SQLite as the only persistence layer: one database per service, with
  `data/verifund.db` owned by the control plane.
- Use a static development ops token for buyer/console-to-control-plane calls
  and HMAC seller transaction tokens for seller calls. No Clerk or hosted
  identity provider.
- Make every money movement idempotent, auditable, recoverable, and testable in
  a deterministic fake mode.
- Preserve `VERIFUND_MODE=off` compatibility for existing tests, demos, and
  protocol payloads.

## 3. Non-goals

- Refunds, disputes, chargebacks, split settlement, multi-seller baskets, or
  fee allocation. v1 is USD only.
- More than one shipment per transaction.
- Live PayPal or production money movement. v1 is Sandbox only.
- Real carrier integration. v1 uses simulated shipment and delivery evidence
  generated by the seller agent.
- Per-seller PayPal API credentials, a separate escrow account, or PayPal
  marketplace features. One platform Business account sends Payouts.
- Multi-tenant identity, KYC, hosted registry, or cloud deployment automation.
- A separate worker, queue, or horizontally scaled control plane. The
  reconciler runs in-process.
- A global review-queue page. The Transaction Room lives inside the existing
  deal room; a queue can be added later.
- AI-based evidence inspection. The control plane's deterministic verification
  policy remains authoritative; the Verifund agent summarizes its results.
- Cryptographically verifiable cross-organization approval attestation beyond
  the agreement hash and HMAC receipts.

## 5. Relationship to the MarketMesh spec

The 2026-10-21 spec forbids payment processing, escrow, and a transaction
coordinator. That remains true for `VERIFUND_MODE=off`, which is the default.

When `VERIFUND_MODE` is `fake` or `sandbox`, this spec supersedes those
non-goals for the Verifund subsystem only. The following constraints remain:

- No runtime import, call, or dependency on `verifund-platform-backend`.
- No parent-backend code, schema, or module is copied; the new subsystem is an
  independent implementation.
- MarketMesh remains the user-facing product; “Verifund” names the settlement
  subsystem.
- The required directory name `verifund-a2a/` remains.
- The A2A protocol, buyer/seller graph boundaries, and console remain
  MarketMesh-owned.

`scripts/check_standalone.py` will stop banning the words `verifund`, `escrow`,
and `transaction coordinator`. It will instead reject imports of the parent
package (`verifund`, `verifund_platform_backend`, `src.verifund`) and filesystem
references to the parent backend. Legitimate modules named
`verifund_control_plane` and `verifund_contracts` remain allowed.

```text
└───────────────┬───────────────────────────────┬────────────────────┘
                │ same-origin Next routes       │ AG-UI
                │ BUYER_CONSOLE_API_TOKEN       │
┌───────────────▼──────────────────┐   ┌────────▼────────────────────┐
│ Buyer agent            :9100     │   │ Orchestrator        :9000   │
│ LangGraph · mandate · approval   │   │ ADK · seller mediation      │
│ console API · settlement · SQLite│   │ secret-ref resolution       │
└───────┬──────────────────┬───────┘   └────────┬────────────────────┘
        │ REST discovery   │ A2A                 │ A2A
┌───────▼──────────┐   ┌───▼─────────────────────▼───────────────────┐
│ Registry :9105   │   │ Sellers :9201–9204                          │
│ Agent Card index │   │ LangGraph · SQLite · evidence outbox        │
└──────────────────┘   │ scoped seller transaction token             │
                       └────────────────────┬───────────────────────┘
                                            │ seller API (HMAC token)
┌───────────────────────────────────────────▼────────────────────────┐
│ Verifund control plane                                localhost:9300│
│ FastAPI · state machine · ledger · evidence · PayPal · reconciler  │
│ SQLite data/verifund.db · evidence data/evidence/<sha256>          │
└───────────────────────────────┬────────────────────────────────────┘
                                │ Orders/Capture/Payouts + webhooks
                     ┌──────────▼──────────┐
                     │ PayPal Sandbox      │
                     │ platform Business   │
                     │ buyer Personal      │
                     │ seller payouts      │
                     └─────────────────────┘
```

The buyer also calls the control plane with the ops token. The orchestrator
resolves seller tokens from the buyer’s internal endpoint. A Verifund A2A
service (default port `9301`) is discovered through generic-agent registry
endpoints, separate from seller catalog discovery. It calls authenticated
buyer settlement routes and never receives the control-plane ops token or
PayPal credentials. The console never calls the control plane directly.

```text
Orchestrator :9000 ──A2A──> Verifund agent :9301
                                  │ authenticated buyer settlement API
                                  ▼
                            Buyer :9100 ──ops token──> Control plane :9300
```

### 6.2 Service responsibilities

| Service | Owns | Does not own |
|---|---|---|
| Buyer agent | Mandate, discovery, negotiation, buyer approval, settlement orchestration/projection | Money, capture IDs, payout authority, ledger |
| Orchestrator | Console AG-UI, seller A2A mediation, seller-token secret-ref resolution | Money, transaction state, buyer award authority |
| Verifund A2A agent | Assemble a proposal from the Buyer award, coordinate bilateral review tasks, status/evidence workflow, checkout handoff, reviewer interaction requests, receipt retrieval through buyer APIs | Setting terms independently of the award, verification policy, funds, payout, control-plane ops credential, PayPal credentials |
| Seller agents | Catalog, offers, stock reservation, order creation, evidence upload outbox | Release, payout, transaction state authority |
| Control plane | Agreement hash, transaction state, held-funds ledger, evidence metadata, verification policy, PayPal calls, webhooks, payout, receipts, audit | Seller catalog, negotiation, buyer mandate |
| Console | Presentation, reviewer actions proxied through buyer, receipt display | Ops token, seller token, direct control-plane access |
| PayPal Sandbox | Card/payer approval, capture, payout rails, webhook delivery | Business rules, release policy, receipt signing |

### 6.3 Trust boundaries

| Surface | Caller | Credential |
|---|---|---|
| Browser → Next.js route handlers | Browser | Local console; no control-plane token in the browser |
| Next.js → buyer console API | Console server | Existing `BUYER_CONSOLE_API_TOKEN` via `x-marketmesh-console-token` |
| Buyer agent → control plane | Buyer service | Static `VERIFUND_OPS_TOKEN` bearer |
| Seller agent → control plane | Seller service | Short-lived HMAC seller transaction token |
| Orchestrator → buyer internal token endpoint | Orchestrator service | `BUYER_INTERNAL_TOKEN`; returns only a token bound to the run/transaction |
| Orchestrator → seller A2A | Orchestrator service | Existing seller A2A token; settlement token injected after resolution |
| Orchestrator → Verifund A2A | Orchestrator service | `Authorization: Bearer $VERIFUND_AGENT_A2A_TOKEN`; card fetched from `$VERIFUND_AGENT_URL/.well-known/agent-card.json` |
| Verifund A2A → buyer settlement API | Verifund service | `x-verifund-agent-token: $VERIFUND_AGENT_INTERNAL_TOKEN`; buyer keeps and applies the control-plane ops token |
| Registration job → registry agents API | One-shot registration process | `Authorization: Bearer $REGISTRY_ADMIN_TOKEN`; runs outside the agent runtime and exits |
| Registry → Verifund Agent Card | Registry service | Public card fetch restricted by `ALLOWED_CARD_HOSTS`; Compose adds `verifund-agent` |
| PayPal → control plane | PayPal | PayPal webhook signature verification |
| Browser → fake checkout / PayPal return | Buyer’s browser | Signed, short-lived URL token |

The console never talks to the control plane directly. The buyer keeps the ops
token server-side and proxies reviewer actions. The Verifund A2A agent uses a
separate internal service credential to call the buyer; the browser and LLM do
not receive it. The agent's A2A bearer token authenticates the orchestrator to
`/a2a` and is distinct from the buyer-internal token. The runtime agent process
never receives `REGISTRY_ADMIN_TOKEN`; only the short-lived registration job
does.

### 6.4 Data ownership

- Control plane: `data/verifund.db`; evidence files under `data/evidence/`.
- Buyer: `data/buyer.db` plus new `run_settlement` and `run_secrets` tables.
- Seller: each seller’s existing SQLite database plus `settlement_tokens` and
  `evidence_outbox` tables.
- Registry seller catalog tables/routes remain unchanged; generic A2A agent records use a separate table and endpoints.
- No service reads another service’s SQLite file.

## 7. Domain model

### 7.1 Entities

**Transaction**

| Field | Meaning |
|---|---|
| `transaction_id` | Stable ID (`vf_...`) generated by the control plane |
| `run_id` | Buyer run ID |
| `buyer_id`, `seller_id` | Parties |
| `offer_id` | Winning offer |
| `state` | Domain state |
| `version` | Optimistic concurrency guard |
| `last_seq` | Last transaction event sequence |
| `amount_cents`, `currency` | USD integer cents |
| `agreement_id`, `agreement_hash`, `agreement_version` | Binding terms |
| `seller_decision` | Seller acceptance or rejection receipt |
| `approval` | Buyer approval receipt |
| `buyer_agent_review` | Buyer agent's hash-bound terms/mandate validation; distinct from human funding approval |
| `funding` | PayPal order, capture, checkout URL, status |
| `purchase_order` | Seller order snapshot, tracking, ETA |
| `evidence_summary` | Required/received kinds, hashes, deadlines |
| `verification` | Checks, reasons, policy result |
| `payout` | Batch/item IDs, status, amount |
| `receipt` | Signed receipt metadata |
| `deadlines` | Funding, evidence, inspection, payout alert |
| `created_at`, `updated_at` | Timestamps |

**Agreement v1** is assembled by the Verifund agent only from the Buyer award
and contains the commercial terms used for the hash: transaction, run, buyer,
seller, offer, currency, amount, quantity, line items, shipping cents, delivery
days, warranty months, returns days, and creation time. The control plane
validates totals, assigns the version, canonicalizes the terms, and computes the
authoritative hash. It does not contain the buyer’s shipping address or payment
credentials.

**Ledger entry** is a double-entry pair with accounts such as
`platform_cash`, `held_funds`, `seller_payable`, and `seller_paid`. Every
capture and payout writes balanced entries in the same database transaction as
the state change.

**Evidence** stores `evidence_id`, `transaction_id`, `seller_id`, `kind`,
`sha256`, `media_type`, `size_bytes`, `original_filename`, `note`, and
`created_at`. Bytes live at `data/evidence/<sha256>`; the database stores only
metadata.

### 7.2 State machine

```text
AWARDED
  ├─ buyer agent or seller rejects hash ─► CANCELED
  └─ both agents accept same hash ──────► AGREED
       └─ human approves + funding starts ─► FUNDING_PENDING
            └─ capture completed ────────► FUNDED
                 └─ purchase order reported ─► FULFILLMENT_PENDING
                      └─ first evidence received ─► VERIFICATION_PENDING
                           ├─ policy passes ─────► RELEASE_PERMITTED
                           └─ policy fails ──────► REVIEW_REQUIRED
                                └─ reviewer override ─► PAYOUT_PENDING
RELEASE_PERMITTED
  └─ reviewer release ─────────────────► PAYOUT_PENDING
       └─ payout succeeded ────────────► RELEASED
```

Side states:

- `REVIEW_REQUIRED`: paused, non-terminal; reviewer can release with override
  (if funds are captured and the ledger is consistent), retry payout, cancel
  before capture, or leave for manual resolution.
- `CANCELED`: terminal; allowed only before capture. Set by a buyer/reviewer
  cancel, a reported seller rejection, or funding expiry. A confirmed late
  capture moves it to `REVIEW_REQUIRED` rather than ignoring the funds.
- `FAILED`: terminal; capture declined, non-retryable payout failure, or
  exhausted retries with no recoverable path. A confirmed late capture moves it
  to `REVIEW_REQUIRED` rather than discarding the funds.
- `RELEASED`: terminal under normal conditions; a later payout refund or
  reversal reopens it as `REVIEW_REQUIRED` and flags the existing receipt for
  manual review.

Transition rules:

| From | To | Guard |
|---|---|---|
| — | `AWARDED` | Award created; agreement v1 hashed; seller payout email resolved |
| `AWARDED` | `AGREED` | Buyer-agent review and seller acceptance both match transaction and current agreement version/hash |
| `AWARDED` | `CANCELED` | Buyer-agent or seller-agent rejection reported; no capture exists |
| `AGREED` | `FUNDING_PENDING` | Human funding approval exists and binds the current hash; PayPal/fake order created |
| `FUNDING_PENDING` | `FUNDED` | Capture completed and amount/currency match |
| `FUNDED` | `FULFILLMENT_PENDING` | Purchase order reported; hash/amount match |
| `FULFILLMENT_PENDING` | `VERIFICATION_PENDING` | Purchase order recorded and at least one evidence item stored |
| `VERIFICATION_PENDING` | `RELEASE_PERMITTED` | Policy passes |
| `VERIFICATION_PENDING` | `REVIEW_REQUIRED` | Policy fails or evidence deadline expires |
| `RELEASE_PERMITTED` | `PAYOUT_PENDING` | Reviewer release; payout intent row committed |
| `PAYOUT_PENDING` | `RELEASED` | Payout item succeeded; receipt created |
| `RELEASED` | `REVIEW_REQUIRED` | Payout item refunded or reversed after release |
| `PAYOUT_PENDING` | `REVIEW_REQUIRED` | Payout refunded, reversed, or unclaimed past 30 days |
| `REVIEW_REQUIRED` | `RELEASED` | A previously pending payout item later succeeds |
| `REVIEW_REQUIRED` | `PAYOUT_PENDING` | Reviewer retries a retryable payout failure |
| `REVIEW_REQUIRED` | `CANCELED` | No capture exists; buyer/reviewer cancel |
| `AGREED`, `FUNDING_PENDING` | `CANCELED` | No capture exists; buyer/reviewer cancel, or funding expiry in `FUNDING_PENDING` |
| `CANCELED` | `REVIEW_REQUIRED` | A capture is confirmed after cancellation |
| `FAILED` | `REVIEW_REQUIRED` | A capture is confirmed after a decline or failure |
| Any non-terminal | `REVIEW_REQUIRED` | Flagged anomaly or provider ambiguity |
| `PAYOUT_PENDING` | `FAILED` | Non-retryable payout failure or exhausted retries |
| `FUNDING_PENDING` | `FAILED` | Capture declined after a payment attempt |

Every transition uses `WHERE transaction_id = ? AND version = ? AND state = ?`.
Zero updated rows means `409 conflict`. `version` increments on every write.
`last_seq` increments only when a transaction event is appended.

### 7.3 Agreement and hash binding

`agreement_hash = sha256(canonical_json(agreement))`, where canonical JSON uses
sorted keys, compact separators, UTF-8, and integer cents. The hash binds:

- the A2A `AcceptOffer` and seller rejection report;
- the buyer-agent agreement review;
- the seller-agent agreement decision;
- the buyer approval;
- the funded `PurchaseOrderRequest`;
- the seller transaction token;
- the release permit;
- the receipt.

The hash is stored with agreement version. A mismatch returns
`409 hash_mismatch` and moves no money. The model supports agreement versions.
Buyer and seller agent decisions must reference the same current version/hash;
a counterproposal creates a new version and requires both agents to review it
again. The old hash is rejected for subsequent decisions.

Buyer-agent review records the transaction ID, agreement version/hash, A2A task
ID, timestamp, decision, and reason. It validates the exact terms against the
selected award and buyer mandate; it does not authorize payment. Human funding
approval separately records the transaction ID and hash shown in the chat HITL
card. On resume, the graph verifies that the current transaction still has
that hash. The graph does not trust hash fields supplied by the browser.

### 7.4 Money and ledger

- All amounts are integer USD cents; floating point is forbidden in money paths.
- Capture must equal the agreement amount and currency.
- The ledger invariant after capture is `held_funds == captured`.
- The ledger invariant after release is `seller_paid == agreement amount` and
  `held_funds == 0`.
- PayPal fees are not allocated in v1; the seller receives the agreement
  amount, and any fee differences are platform-owned.
- No ledger entry is written without a corresponding state transition and
  idempotency record.
- The reconciler verifies ledger completeness for every `RELEASED` transaction.

### 7.5 Events and projection

Each transaction has an append-only `transaction_events` stream with
`seq`, `type`, `payload`, `actor`, and `created_at`. The compact projection
`GET /transactions/{id}/state` includes `last_seq`.

The buyer polls that one endpoint and appends a trace event (and any active
AG-UI settlement status) only when `last_seq` advances. It stores `last_projected_seq` in its `run_settlement`
table, so repeated polls cannot duplicate trace events. The projection contains
no tokens, ledger entries, buyer address, or other transactions.

Event types include `award_created`, `seller_accepted`, `seller_rejected`,
`buyer_approved`, `funding_required`, `funded`, `purchase_order_reported`,
`evidence_received`, `verification_passed`, `verification_failed`,
`release_permitted`, `release_authorized`, `payout_pending`, `released`,
`review_required`, `canceled`, `failed`, and `settlement_error`.

### 7.6 Receipts

A receipt payload contains:

```json
{
  "receipt_version": 1,
  "transaction_id": "vf_...",
  "agreement_hash": "...",
  "amount_cents": 123400,
  "currency": "USD",
  "buyer_id": "demo-buyer",
  "seller_id": "northwind-audio",
  "capture_id": "PAYPAL-CAPTURE-ID",
  "payout_item_id": "PAYPAL-PAYOUT-ITEM-ID",
  "evidence_hashes": ["...", "..."],
  "released_at": "2026-10-27T12:34:56Z"
}
```

`payload_hash = sha256(canonical_json(payload))`.
`signature = HMAC-SHA256(receipt_key, payload_hash)`, encoded as base64url.
`kid` identifies the signing key from `VERIFUND_RECEIPT_KEYS`;
`VERIFUND_RECEIPT_ACTIVE_KID` selects the signing key. Old keys remain
available for verification during rotation.

`GET /transactions/{id}/receipt` returns `payload`, `payload_hash`,
`signature`, `kid`, and `verified`. The console displays the verified badge
from the control-plane result; it never receives the receipt key.

## 8. End-to-end lifecycle

### 8.1 Award, acceptance, and rejection

1. The buyer ranks offers and selects a winner.
2. The orchestrator sends the exact structured award to the Verifund A2A agent
   using `verifund.agreement.create`. Verifund assembles agreement terms without
   changing the award, then calls the buyer's authenticated internal agreement
   route. The buyer uses its control-plane client to validate totals, resolve
   seller payout configuration, create the transaction in `AWARDED`, assign
   agreement version 1, and compute the canonical hash. The result includes the
   agreement projection, transaction ID, version, hash, and seller token
   reference. Only the seller token itself remains in the buyer's secret store.
3. The orchestrator sends the same agreement projection/version/hash to the
   Buyer A2A review skill. The Buyer verifies it against the selected offer and
   mandate, records its accepted/rejected decision through its own
   control-plane client, and pauses with `seller_review_required` for an
   accepted decision. The recorded review carries the hash, A2A task ID,
   timestamp, and reason. A rejected decision cancels the transaction and never
   reaches Seller review. This is agent validation, not human funding approval.
4. Only after Buyer acceptance, the orchestrator sends the same agreement to the
   Seller A2A agreement-review skill. The Seller verifies seller ID, hash,
   amount, line items, terms, and fulfillment ability, and returns a structured
   accepted/rejected decision tied to that hash. Seller agreement review does
   not reserve stock or move money.
5. After the Seller responds, the orchestrator resumes the original Buyer A2A
   task with the exact structured Seller decision; the Buyer reports `/accept`
   or `/reject` through its control-plane client. The control plane records each
   party, decision, agreement version/hash, task ID, timestamp, and reason. It
   moves the transaction to `AGREED` only when both agent decisions accept the
   same current hash. Repeated reports are idempotent.
6. If either agent rejects or returns a counterproposal, no funding approval is
   requested. Rejection cancels the unfunded transaction with a reason. A
   counterproposal requires a new agreement version/hash and a fresh review by
   both agents. Transport/protocol errors remain pending and are retried or
   surfaced; they never count as acceptance.

The seller token is only for transaction reads and evidence writes; it cannot
approve, release, or pay out. The buyer's graph carries a
`settlement_secret_ref` instead of the token; the orchestrator resolves and
injects the token at A2A seller-send time (§11.2). The orchestrator coordinates
the remote A2A tasks but does not edit agreements, record approvals itself, or
decide whether either party accepted.

### 8.2 Approval and funding

1. After both agents accept, the control plane state is `AGREED`. The buyer
   exposes the exact control-plane agreement projection and both hash-bound
   decision receipts.
2. The orchestrator asks `verifund.transaction.status` for the buyer projection
   and both hash-bound decisions, then prepares that projection for the human.
   CopilotKit renders a HITL card in chat with the immutable terms, buyer-agent
   validation, and seller-agent acceptance. The agent cannot alter the binding
   terms; any change requires a new version and both agents review the new hash.
3. The structured HITL response is bound to the transaction ID, agreement
   version, and agreement hash and is passed to `verifund.transaction.fund` as a
   `FundingApprovalDecision`. On rejection, the agent calls the buyer's
   `approve-funding` route; the buyer cancels with `buyer_rejected` and no
   checkout is created. On approval, the same route records the human approval
   and calls `POST /transactions/{id}/fund` through the buyer's control-plane
   client. Agent assent never substitutes for this decision.
4. The control plane creates a PayPal Sandbox or fake order idempotently,
   transitions to `FUNDING_PENDING`, and returns a payer-action URL. The agent
   returns `checkout_url`/`expires_at`, and a CopilotKit frontend tool renders
   the checkout handoff in chat. Sandbox payer approval occurs on PayPal's
   hosted page; the application does not collect PayPal credentials in chat.
5. PayPal return/webhook or polling confirms capture. The control plane checks
   amount/currency, records the capture and ledger entries, and transitions to
   `FUNDED`. The buyer's run projection updates the chat thread; the Verifund
   agent reports success only after reading that confirmed state.

A buyer cancel before capture transitions to `CANCELED`. A declined capture
transitions to `FAILED`. A pending or ambiguous capture remains
`FUNDING_PENDING` and is polled. A seller rejection is accepted only while the
transaction is `AWARDED`; once the seller has accepted, the agreement is
binding and the seller cannot unilaterally reject it.

### 8.3 Fulfillment and evidence

1. On `FUNDED`, the buyer refreshes the seller token if it is near expiry,
   then sends the A2A `PurchaseOrderRequest` with `settlement_transaction_id`,
   `agreement_hash`, and the current `settlement_token`.
2. The seller calls the seller transaction endpoint and requires `FUNDED` (or a
   later fulfilled state) before reserving stock. It replaces any stored token
   with the token in the purchase order, creates the order as today, and returns
   it. A repeated purchase order with the same idempotency key returns the
   existing order.
3. The buyer reports the purchase order with
   `POST /transactions/{id}/purchase-order`. The control plane stores the
   seller order snapshot and transitions to `FULFILLMENT_PENDING`.
4. The seller’s evidence outbox uploads a shipment manifest and a delivery
   confirmation to the seller evidence endpoint. The uploads use the seller
   token and are retried independently of order confirmation.
5. The control plane stores evidence content-addressed by SHA-256 and
   transitions to `VERIFICATION_PENDING` on the first item once the purchase
   order is recorded. If evidence arrives before the purchase-order report, it
   is stored while the transaction is `FUNDED`; the transition happens when
   both conditions are satisfied. Duplicate hashes are treated as success.

Evidence v1 is a shipment manifest (carrier, tracking number, shipped time, line
items) and a delivery confirmation (delivered time, recipient/signature). The
demo seller generates these; real carrier integration is deferred. Manual
upload remains available through the seller API.

### 8.4 Verification and release

Verification runs when all required evidence kinds are present, when the
evidence deadline expires, or when `POST /verify` is called. With incomplete
evidence before the deadline, the transaction stays `VERIFICATION_PENDING`; an
early partial upload never moves it to review.

The verification policy checks:

- required evidence kinds are present and readable;
- evidence hashes match stored bytes;
- seller ID and agreement hash match;
- purchase-order tracking matches the shipment manifest;
- delivery is not in the future;
- the inspection window after delivery has elapsed;
- amount and currency match;
- evidence deadline and inspection window are satisfied;
- no open review flag exists;
- the ledger is complete for the captured amount.

If the only unmet condition is a future inspection window, the transaction stays
`VERIFICATION_PENDING` and the reconciler re-runs verification when the window
elapses. A future inspection window is not a policy failure and never produces
`REVIEW_REQUIRED`.

A pass produces `RELEASE_PERMITTED`. A failure produces `REVIEW_REQUIRED` with
machine-readable reasons. The Verifund agent summarizes the policy result and
evidence references in chat; the Transaction Room retains the complete evidence
detail.

A reviewer releases through a separate CopilotKit HITL card in chat, which
shows the transaction, verification result, evidence summary, and any override
reasons. A rejection leaves the transaction unreleased. An approval is bound to
the transaction ID and agreement hash and calls the buyer's release API. The
buyer calls `POST /transactions/{id}/release`. From
`RELEASE_PERMITTED`, this is the normal path. From `REVIEW_REQUIRED`, the
request must include `override: true` and a non-empty note; the override is
written to the audit log. Override is allowed only for verification/policy
failures. Funding amount/currency mismatches, ledger inconsistencies, and late
captures remain in review for manual resolution and cannot be overridden. The
control plane records open review reasons and accepts an override only when
every reason is in the overridable verification set. Non-overridable reasons
(funding mismatch, ledger inconsistency, late capture) require out-of-band
resolution in the PayPal dashboard; v1 implements no refunds or ledger
corrections from the console, so those transactions remain in
`REVIEW_REQUIRED`. The control plane commits the payout intent and transitions
to `PAYOUT_PENDING` before calling PayPal. It does not auto-release on a timer.

### 8.5 Payout and receipt

1. The control plane calls PayPal Payouts with a stable `sender_batch_id` and
   `sender_item_id`, the seller payout email, the agreement amount, and a note.
2. Payout item webhooks or polling update the item status. A `SUCCESS` item
   status (or `PAYMENT.PAYOUTS-ITEM.SUCCEEDED` event) transitions to `RELEASED`;
   retryable statuses stay `PAYOUT_PENDING`; terminal failures become `FAILED`.
3. On `RELEASED`, the control plane writes the receipt, verifies ledger
   completeness, and exposes it at the receipt endpoint.
4. The buyer polls the compact state, fetches the receipt when available, and
   finalizes the run at stage `released`. The Verifund agent presents the
   verified receipt in chat; the Transaction Room shows the same receipt and
   transaction history.

The platform Business account receives the capture and sends the payout. This
is a platform-held-funds model, not a PayPal escrow product.

### 8.6 Off mode

`VERIFUND_MODE=off` keeps the existing graph sequence:

```text
rank_offers → await_approval → place_order (accept + PO) → finalize
```

No control-plane calls, no new stages, no Transaction Room data, and no new
contract fields. Existing tests and demos must pass unchanged.

## 9. API surface

All amounts are integer cents. All ops requests accept `Idempotency-Key` and
carry `x-verifund-actor` (for example `buyer-agent` or `console:reviewer`) and
an optional `x-request-id`.

Control-plane routes are unprefixed: there is no `/v1` path segment. Every path
below is absolute from the control-plane base URL. Only PayPal’s own REST API
uses `/v1` paths.

### 9.1 Ops API (bearer `VERIFUND_OPS_TOKEN`)

```text

GET /transactions
GET /transactions/{id}
GET /transactions/{id}/state
GET /transactions/{id}/events
GET /transactions/{id}/receipt
GET /transactions/{id}/evidence

POST /transactions/{id}/approve

POST /transactions/{id}/verify
POST /transactions/{id}/release
POST /transactions/{id}/payout
POST /transactions/{id}/payout/refresh
POST /transactions/{id}/cancel
POST /transactions/{id}/flag-review
POST /transactions/{id}/seller-token
POST /transactions/{id}/seller-token/revoke
POST /reconciler/run
```

`GET /transactions` supports `run_id`, `state`, and `seller_id` filters.

funding approval. The control plane transitions `AWARDED` to `AGREED` only after
the Buyer review and Seller acceptance both accept the same current hash.
`POST /funding/refresh`, `POST /payout/refresh`, and `POST /verify` force one
reconciliation or policy re-evaluation and are idempotent. `POST /seller-token`
reissues a seller token and revokes the previous one; `/revoke` invalidates the
current token. `POST /flag-review` requires a reason and moves a non-terminal
transaction to `REVIEW_REQUIRED`. Evidence reads return the stored bytes with
the recorded media type and an attachment filename; they never expose
filesystem paths.

### 9.2 Seller API (seller transaction token)

```text
GET /seller/transactions/{id}
GET /seller/transactions/{id}/evidence
POST /seller/transactions/{id}/evidence
GET /seller/transactions/{id}/evidence/{evidence_id}
```

`POST /evidence` is multipart with `kind`, `file`, optional `note`, and optional
`captured_at`. Supported kinds are `shipment_manifest`,
`delivery_confirmation`, `invoice`, and `other`. Supported media types are JSON,
plain text, PDF, PNG, and JPEG, with a configurable size limit.

The seller projection includes agreement terms, amount, deadlines, order and
tracking, evidence status, and transaction state. It excludes buyer approval
internals, ledger entries, receipt keys, and other transactions.

Evidence uploads are accepted in `FUNDED`, `FULFILLMENT_PENDING`, and
`VERIFICATION_PENDING`. Uploads after `RELEASE_PERMITTED` or a terminal state
are rejected with `invalid_state`.

### 9.3 Checkout and webhook API

```text
GET/POST /checkout/fake/{token}  fake mode only
GET /return/{token}              sandbox mode only
GET /cancel/{token}              sandbox mode only
POST /webhooks/paypal            fake and sandbox
```

The fake checkout page displays amount and seller with Approve and Cancel. It
collects no credentials and is not registered in sandbox mode. The fake link is
signed, short-lived, and one-time.

The PayPal return route captures idempotently and redirects to the console run

### 9.4 Buyer console API

The buyer exposes these same-origin routes to the console:

```text
GET /api/runs/{run_id}
GET /api/runs/{run_id}/settlement
POST /api/runs/{run_id}/settlement/advance
POST /api/runs/{run_id}/settlement/release
POST /api/runs/{run_id}/settlement/review
POST /api/runs/{run_id}/settlement/cancel
GET /api/runs/{run_id}/settlement/receipt
GET /api/runs/{run_id}/settlement/evidence/{evidence_id}
POST /internal/settlement/seller-token
```

All `/api/runs/{run_id}/settlement` routes require `x-marketmesh-console-token`;
the buyer adds the ops token server-side. `GET /api/runs/{run_id}` includes the
settlement projection only when that console token is valid, so legacy callers
still receive the run without financial data. The Next.js run route adds the
token.
`GET /api/runs/{run_id}` lazily refreshes the settlement projection and returns
it alongside the run, so the console’s existing run poll updates the Transaction
Room without a second polling loop. If the control plane is unavailable, the
buyer returns the last projection with `settlement_unavailable: true` and does
not fail the run read.

`POST /settlement/advance` resumes the current funding/release/verification
interrupt. `POST /settlement/release` is the reviewer release/override action.
`POST /settlement/review` handles `flag_review` and `retry_payout`.
`POST /settlement/cancel` cancels before capture and carries
`reason_code: buyer_rejected`, `buyer_cancelled`, or `reviewer_cancelled`. A
seller rejection is reported by the buyer internally and appears in the
projection; the console does not need a seller-reject action. Reviewer actions
use actor `console:reviewer`; advance uses `buyer-agent`. Repeated actions are
idempotent.
A per-run lock prevents the executor and the settlement API from resuming the
same graph simultaneously; a second caller gets `409 conflict`.

`POST /internal/settlement/seller-token` is not browser-facing and is never
mounted on the public console proxy. It requires
`x-marketmesh-internal-token: $BUYER_INTERNAL_TOKEN`, accepts
`{run_id, transaction_id, seller_id, purpose}`, verifies that the run and
transaction match the stored settlement secret, and returns the current seller
token and expiry. The orchestrator calls it immediately before an A2A seller
send.

The Verifund A2A service uses authenticated internal routes, never mounted
through Next.js:

```text
GET  /internal/runs/{run_id}/settlement
POST /internal/runs/{run_id}/settlement/agreement
POST /internal/runs/{run_id}/settlement/approve-funding
POST /internal/runs/{run_id}/settlement/release
GET  /internal/runs/{run_id}/settlement/receipt
GET  /internal/runs/{run_id}/settlement/evidence/{evidence_id}
```

Every route requires `x-verifund-agent-token: $VERIFUND_AGENT_INTERNAL_TOKEN`
and validates the run/transaction/version/hash binding. They are not mounted
through Next.js. The routes are:

- `GET /settlement` returns the buyer projection, `agreement`,
  `agreement_version`, `agreement_hash`, and `seller_token_ref`. It never
  returns `seller_token` or `ops_token`.
- `POST /settlement/agreement` accepts the exact award plus the original buyer
  task/context IDs, has the buyer call control-plane `POST /awards`, and returns
  the canonical `AgreementProjection` with the same binding fields. Repeated
  calls with the same idempotency key replay the stored agreement.
- `POST /settlement/approve-funding` accepts a structured
  `FundingApprovalDecision`. A rejection calls the buyer's cancel path with
  `buyer_rejected`; an approval records the human approval and calls
  `POST /transactions/{id}/fund`. Both paths are idempotent and return the
  updated projection plus the checkout handoff when one was created.
- `POST /settlement/release` accepts a structured `ReleaseApprovalDecision`,
  including the override flag and note, and calls the buyer's release flow.
- `GET /settlement/receipt` and
  `GET /settlement/evidence/{evidence_id}` return only the requested data.

Buyer-agent review and the seller's decision are reported by the Buyer agent
through its own `POST /buyer-review`, `/accept`, or `/reject` client calls;
Verifund does not submit or rewrite either decision. All downstream operations
use the buyer's control-plane client. The control-plane ops token is never
returned or forwarded to the Verifund service.

### 9.6 Verifund A2A interface

The Verifund service publishes an A2A Agent Card at
`$VERIFUND_AGENT_URL/.well-known/agent-card.json` and serves JSON-RPC at
`/a2a`, both on `VERIFUND_AGENT_PORT` (default `9301`). It is registered through
the registry's generic-agent endpoints, separate from seller registration and
catalog discovery. Registration is a one-shot admin job:

```text
POST $REGISTRY_URL/v1/agents
Authorization: Bearer $REGISTRY_ADMIN_TOKEN
{"agent_id": "verifund", "card_url": "$VERIFUND_AGENT_CARD_URL"}
```

The registry fetches and validates the card, stores it in the separate `agents`
table, and exposes it through `/v1/agents` and `/v1/agents/discover`. The
runtime agent never receives `REGISTRY_ADMIN_TOKEN`. The Agent Card, `/health`,
and `/ready` are public; `POST /a2a` requires
`Authorization: Bearer $VERIFUND_AGENT_A2A_TOKEN`. The agent uses the existing
structured commerce payload conventions. The initial skills are:

| Skill ID | Purpose | Human gate |
|---|---|---|
| `verifund.agreement.create` | Assemble an agreement proposal from the exact Buyer award; request buyer validation and canonicalize/store through the buyer API | No direct human gate; cannot change award terms |
| `verifund.transaction.status` | Return current transaction state and confirmed provider status | None |
| `verifund.transaction.fund` | Submit the structured human funding approval/rejection through the buyer and return the checkout handoff | Separate HITL approve/reject; rejection cancels before checkout |
| `verifund.evidence.review` | Summarize evidence metadata and deterministic policy outcome | Reviewer HITL when release is permitted or review is required |
| `verifund.transaction.release` | Submit an approved, transaction/hash-bound release decision through the buyer | Separate HITL approve/reject; override requires a note |
| `verifund.receipt.get` | Retrieve and present the signed receipt after release | None |

The Buyer A2A agent adds `commerce.agreement.review`; it validates the proposal
against the award and mandate, returning an explicit accept/reject decision,
hash, task ID, timestamp, and reason. The Seller A2A agent adds
`commerce.agreement.review`; it validates its identity, offer terms, and ability
to fulfill, returning the same decision envelope. Neither skill changes terms
or moves money.

The orchestrator calls agents sequentially: Verifund creates the proposal, the
Buyer reviews it on the original Buyer task, then the Seller reviews it. The
orchestrator preserves the exact agreement/hash and task correlation IDs; after
Seller responds, it resumes the Buyer task with the Seller decision. It does not
rewrite either decision or infer consent. A rejection or counterproposal
prevents the human funding card; changed terms require a new agreement
version/hash and both reviews again. Transport failures remain
pending/retryable, never accepted.

Requests identify the run and transaction; mutating requests also carry the
stored agreement hash and an idempotency key. The agent returns structured task
status, transaction state, agreement hash, and any required next action. It
never treats free-form chat text as approval or claims capture, payout, or
receipt completion until the buyer projection confirms it. The agent calls
only authenticated buyer internal settlement routes; those routes invoke the
buyer's control-plane client.

CopilotKit `useHumanInTheLoop` cards collect the human's explicit funding
approval only after both agent decisions are accepted, and the later payout
release approval. `useFrontendTool` / `useRenderTool`
provide typed checkout handoff, evidence/status rendering, and receipt display.
The checkout tool opens the hosted PayPal payer-action URL (or fake checkout);
PayPal credentials are never collected in chat. The Transaction Room reads the
same buyer projection and remains the detailed evidence/history view.

## 10. PayPal integration

### 10.1 PaymentPort

```python
class PaymentPort(Protocol):
    async def create_order(txn, *, return_url, cancel_url, idempotency_key): ...
    async def capture_order(order_id, *, idempotency_key): ...
    async def get_order(order_id): ...
    async def create_payout(txn, *, seller_email, batch_id, item_id): ...
    async def get_payout_item(item_id): ...
    async def verify_webhook(headers, raw_body): ...
```

The same capture and payout services are used by webhooks, polling, fake
checkout, and the reconciler. The adapter only translates HTTP; business rules
stay in the control-plane service.

### 10.2 Sandbox adapter

- Base URL: `https://api-m.sandbox.paypal.com`; refuse the live host in v1.
- OAuth 2 client-credentials token with caching.
- Orders v2 with `intent=CAPTURE`, a single purchase unit, `user_action=PAY_NOW`,
  return/cancel URLs, and `PayPal-Request-Id`.
- Capture with `POST /v2/checkout/orders/{id}/capture` and a stable request ID.
- Payouts with `POST /v1/payments/payouts`, stable `sender_batch_id` and
  `sender_item_id`, and the seller payout email.
- Payout item status via `GET /v1/payments/payouts-item/{id}`.
- Webhook verification via `POST /v1/notifications/verify-webhook-signature`
  using the webhook ID, raw body, and transmission headers.

### 10.3 Fake adapter

The fake adapter persists fake orders and payouts in SQLite and serves its own
checkout approval flow. It does not reuse the parent backend’s
`SandboxPayPalAdapter` or its unsupported `simulate_buyer_approval`.

Scenario knobs cover:

- order-create failure;
- capture pending;
- capture declined;
- amount/currency mismatch;
- payout failure;
- duplicate or delayed webhook;
- unknown transaction;
- crash between provider call and DB write.

The fake adapter is the default for CI and local demos.

### 10.4 Webhooks

- Verify the PayPal signature against the raw body before parsing.
- Dedupe by unique `event_id`; store the raw payload hash.
- Return `200` for duplicates and unmatched events; `500` for transient
  processing failures so PayPal retries.
- Store unmatched/failed events for reconciler retry.
- In fake mode, webhook intake accepts only the test header
  `x-verifund-fake-webhook` matching `VERIFUND_FAKE_WEBHOOK_SECRET`; it never
  claims to have verified a PayPal signature.
- Use `PAYMENT.CAPTURE.COMPLETED`, `PAYMENT.CAPTURE.PENDING`,
  `PAYMENT.CAPTURE.DECLINED`, and refund/reversal events for capture state.
- Use payout item events or `GET payouts-item/{id}` for item status. Batch
  Payouts webhooks are not authoritative for item status.
- Do not rely on `CHECKOUT.ORDER.COMPLETED`; it is marketplace/platform-only.
- Use the Payments v2 `PAYMENT.CAPTURE.DECLINED` event, not the v1 `DENIED`
  spelling.


Codes: `unauthorized`, `forbidden`, `not_found`, `conflict`, `invalid_request`,
`invalid_state`, `hash_mismatch`, `token_expired`, `token_scope_denied`,
`evidence_too_large`, `unsupported_media_type`, `provider_unavailable`,
`provider_rejected`, `provider_ambiguous`, `internal`.

| Failure | Resulting state | Behavior |
|---|---|---|
| Missing/invalid credential | Unchanged | `401/403`, no side effects |
| Seller token wrong transaction/scope/expired | Unchanged | `401/403`; reissue required |
| Agreement hash mismatch | Unchanged | `409`; no money moves |
| Duplicate award/funding/payout | Unchanged or pending | Idempotent replay |
| PayPal order create timeout/5xx | `FUNDING_PENDING` | Retry with same request ID; reconciler |
| Funding expires before capture | `CANCELED` | No ledger impact; reconciler cancels |
| Buyer cancels checkout before capture | `CANCELED` | No ledger impact |
| Seller rejects the agreement | `CANCELED` | No ledger impact; no stock reserved; reason recorded |
| Seller reports terms/hash mismatch | `CANCELED` | Buyer reports the stored hash and reason; no money moves |
| Late capture after cancel or failure | `REVIEW_REQUIRED` | Funds cannot be ignored |
| Capture declined | `FAILED` | No payout; no captured-funds ledger entry |
| Capture pending/ambiguous | `FUNDING_PENDING` | Poll; no fulfillment |
| Capture amount/currency mismatch | `REVIEW_REQUIRED` | No payout; manual resolution only |
| Evidence missing at deadline | `REVIEW_REQUIRED` | No auto-cancel after capture |
| Verification policy fails | `REVIEW_REQUIRED` | Reviewer can override with note |
| Payout timeout/5xx | `PAYOUT_PENDING` | Retry with same batch/item IDs |
| Payout `PENDING`/`ONHOLD`/`UNCLAIMED` | `PAYOUT_PENDING` | Poll; unclaimed beyond 30 days becomes `REVIEW_REQUIRED` |
| Payout `FAILED`/`BLOCKED`/`DENIED` | `FAILED` | No automatic retry |
| Payout `RETURNED` | `FAILED` | Funds returned; manual resolution |
| Payout `REFUNDED`/`REVERSED` | `REVIEW_REQUIRED` | Money returned; human review |
| Invalid webhook signature | Unchanged | `401`; event ignored |
| Duplicate webhook | Unchanged | `200`; deduped |
| Unknown webhook | Unmatched | `200`; reconciler retries |
| Webhook processing error | Pending/unchanged | `500`; PayPal retry + reconciler |
| SQLite busy | Unchanged | `503` + `Retry-After` |
| Crash between provider call and DB write | Pending | Intent row recovered by reconciler |

**Provider-call pattern:** write a `provider_operations` intent row before the
PayPal call, in the same SQLite transaction as the transition to pending. Then
call PayPal. On success, store provider IDs and apply the state change. On
timeout, leave the intent `started`; the reconciler retries with the same
idempotency key or safely confirms the existing provider object. No provider
call happens inside a database transaction.

**Concurrency:** transactions carry a `version` column. Transitions update with
`WHERE id = ? AND version = ? AND state = ?`; zero rows means `409 conflict`.
All money mutations and ledger entries commit atomically.

**Retry/backoff:** provider calls get five attempts with exponential backoff and
jitter. Exhausted funding attempts remain `FUNDING_PENDING` for reconciler or
console retry; exhausted payout attempts become `FAILED`. Reconciler cadence is
configurable: 5 seconds for pending funding/payout in fake, 30 seconds in
sandbox, 60 seconds for deadlines, and 5 minutes for receipts and ledger
completeness.

### 10.6 Reconciler

The in-process reconciler sweeps:

- pending funding orders and captures;
- pending payouts;
- stale `RELEASE_PERMITTED` transactions (metric and audit; no auto-payout);
- evidence deadlines;
- inspection windows;
- unmatched/failed webhooks;
- missing receipts for `RELEASED` transactions;
- ledger completeness and duplicated provider operations;
- provider intents left `started` after a crash.

`POST /reconciler/run` runs one sweep for tests and operations. Each sweep is
idempotent and records a `reconciler_runs` row plus metrics.

## 11. Authentication and security

### 11.1 Credentials

- `VERIFUND_OPS_TOKEN`: static bearer for buyer/control-plane operations. In
  sandbox mode it must be at least 32 bytes and not the default value.
- `BUYER_CONSOLE_API_TOKEN`: existing console-to-buyer token; stays server-side.
- `BUYER_INTERNAL_TOKEN`: orchestrator-to-buyer token for resolving seller
  transaction secrets; never browser-facing.
- `VERIFUND_AGENT_A2A_TOKEN`: bearer that authenticates the orchestrator to the
  Verifund `/a2a` JSON-RPC endpoint. It is distinct from every buyer/seller
  token and is never sent to either agent.
- `VERIFUND_AGENT_INTERNAL_TOKEN`: shared secret sent as
  `x-verifund-agent-token` from the Verifund agent to the buyer's internal
  settlement routes. The buyer stores the expected value and never returns it
  in a projection, receipt, trace, or log.
- `VERIFUND_AGENT_URL` and `VERIFUND_AGENT_CARD_URL`: the agent's public base
  URL and Agent Card URL, used by the orchestrator and the one-shot registration
  job. The card advertises `$VERIFUND_AGENT_URL/a2a`.
- `REGISTRY_ADMIN_TOKEN`: admin bearer used only by the one-shot generic-agent
  registration job. The runtime Verifund agent process never receives it.
- Seller transaction token: compact HMAC token, never used as an ops token.
- PayPal webhook: PayPal signature verification.
- Checkout/return links: signed, short-lived URL tokens.

### 11.2 Seller transaction tokens

Format:

```text
v1.<base64url(payload)>.<base64url(HMAC-SHA256)>
```

Claims: `typ=seller_txn`, `txn`, `seller_id`, `agreement_hash`, `scope`
(`txn:read`, `evidence:write`), `iat`, `exp`, `jti`. Default TTL is 72 hours,
refreshed when the buyer reissues before the purchase order.

- Bound to exactly one transaction, one seller, and the current agreement hash.
- The control plane re-checks all three on every seller request.
- The A2A transport still uses the existing seller agent token;
  `settlement_token` is a payload credential used only against the control
  plane.
- Store only `sha256(jti)` and expiry for audit/revocation; compare HMAC in
  constant time.
- Reissue revokes the previous token. Reissue is allowed only before
  `RELEASE_PERMITTED`; it is rejected once release has been authorized. The
  buyer refreshes the token before sending the funded purchase order when it is
  near expiry, so the seller has a full TTL for evidence uploads; the purchase
  order carries the current token. If evidence uploads can outlast the TTL, the
  buyer reissues again.
- Seller acceptance and rejection are reported by the buyer through the ops
  API; the seller token has no accept/reject scope.
- Never put the token in a URL or log. Redact `settlement_token` and
  `seller_token` in traces.

Seller-token copies in the buyer and seller SQLite files are local demo
storage. They are never exposed through a browser-facing API, trace, or AG-UI
state; the control plane returns the token only to the buyer in award and
seller-token responses. A production deployment would use a secret manager. The
seller removes `settlement_token` from the incoming A2A payload before writing
graph state or checkpoints, stores it in `settlement_tokens`, and injects it
only into the control-plane HTTP call. The buyer keeps its copy in `run_secrets`
and injects it only when sending `AcceptOffer` or `PurchaseOrderRequest`.

The buyer’s seller-call interrupt carries a `settlement_secret_ref`
(`run_id`, `transaction_id`, `seller_id`, `purpose`) instead of the token. The
orchestrator’s `mediate_seller_call` resolves the token from the buyer’s
internal endpoint immediately before the A2A send, injects it into the seller
request, and never places it in LLM context, tool results, AG-UI events,
traces, or logs. The seller’s A2A request logging redacts `settlement_token`
before writing a trace or log.

### 11.3 Ops token and console

All ops requests carry `x-verifund-actor` and optional `x-request-id`; both are
written to the audit log. The console keeps the existing token at the buyer
edge. The browser never sees `VERIFUND_OPS_TOKEN` or a seller token.

### 11.4 Webhook and link verification

- Verify PayPal webhook signatures over the raw body.
- Sign checkout/return links with `VERIFUND_LINK_SECRET`; include `typ`, `txn`,
  `exp`, and `jti`.
- Fake checkout links are one-time; the `checkout_links` table marks them used.
- PayPal return/cancel links expire after 24 hours.

### 11.5 Idempotency

- Ops POSTs accept `Idempotency-Key`; the same key and body replay the stored
  response, while the same key with a different body returns `409`.
- PayPal Orders/Captures use `PayPal-Request-Id`.
- Payouts use a stable `sender_batch_id` and `sender_item_id`.
- Evidence uploads dedupe by SHA-256.
- State transitions are guarded by `version` and `state`.

## 12. Failure semantics

### 12.1 Error envelope

All API errors use the envelope in §10.5. `request_id` is echoed from
`x-request-id` or generated. Provider errors never leak PayPal credentials or
raw card data.

### 12.2 Buyer behavior

- Control plane unreachable: `settlement_unavailable`, retryable; the run stays
  at its current stage.
- Funding returns pending: executor emits `funding_required` with the checkout
  URL; the orchestrator is not blocked.
- Seller refuses the agreement: buyer reports `/reject` with the seller’s reason;
  the run ends `canceled`; no funding.
- Buyer rejects the agreement: buyer calls `/cancel` with `buyer_rejected`; no
  funding.
- Funding fails: `failed`; no purchase order.
- Post-funding seller order failure: buyer calls `flag-review`; run becomes
  `review_required`; no auto-refund in v1.
- Settlement pending: console calls `POST /api/runs/{id}/settlement/advance`;
  repeated clicks are idempotent.
- Released: buyer fetches the receipt and finalizes.
- `review_required` is not terminal; the console keeps polling more slowly so a
  reviewer can resolve it.

### 12.3 Seller behavior

- `AcceptOffer` missing/mismatched hash or transaction ID: reject with
  `invalid_request`/`conflict`; no acceptance.
- Definitive refusal: return an A2A error and do not mark the offer accepted.
  The buyer reports `/reject` with the stored hash and a reason code; the
  seller token cannot mutate the transaction.
- Purchase order missing/mismatched settlement token: reject before reserving
  stock.
- Seller fetches the seller transaction and compares agreement hash, seller ID,
  amount, and funded state before accepting the order.
- Evidence upload runs in a seller-side outbox with retries; order confirmation
  does not depend on it. Duplicate SHA-256 is success.
- The seller never has release or payout authority.

### 12.4 Crash recovery

- Every provider call has an intent row with an idempotency key.
- Reconciler retries or confirms by stable provider IDs.
- State updates and ledger entries commit atomically.
- A crash between provider call and DB write cannot create a second capture or
  payout because retries reuse the same provider idempotency key.
- A crash after capture but before the PO report leaves the transaction
  `FUNDED`; the buyer can resume and report the PO.

## 15. PayPal Sandbox setup

1. **Platform Business account** owns the REST app, webhook ID, and Payouts.
   Record `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`, and
   `PAYPAL_PLATFORM_EMAIL`.
2. **Buyer Personal account** approves checkout. Record
   `PAYPAL_BUYER_EMAIL` for docs/preflight only.
3. **Four seller payout accounts** are mapped by seller ID in
   `VERIFUND_SELLER_PAYOUT_EMAILS`. Emails must be unique, confirmed, able to
   receive Payouts, and distinct from platform/buyer accounts.
4. **Webhook subscription** covers capture completed/pending/declined/refunded
   and payout item succeeded/failed/blocked/denied/returned/refunded/reversed/
   onhold/unclaimed.
5. **Public HTTPS tunnel** exposes return/cancel/webhook URLs through
   `VERIFUND_PUBLIC_BASE_URL`.
6. **Sandbox balance** is added to the platform Business account before payout
   smoke tests.

Docker Compose binds `0.0.0.0` inside the container, publishes only to
`127.0.0.1:9300`, and sets `VERIFUND_ALLOW_PUBLIC_BIND=1`. Sandbox still
requires the public HTTPS tunnel for return/cancel/webhook URLs.

`scripts/verifund_sandbox_preflight.py` validates OAuth, webhook configuration,
HTTPS, secret strength, and the payout-email map. It rejects duplicate payout
emails and payout emails equal to `PAYPAL_PLATFORM_EMAIL` or
`PAYPAL_BUYER_EMAIL`. Sandbox startup refuses default ops/seller/link/receipt
and buyer-internal secrets, a missing webhook ID, the live PayPal host, and
missing seller payout emails.

## 16. Rollout

| Phase | Scope | Exit condition |
|---|---|---|
| 0 | Contracts, workspace, env, standalone guard | Off-mode tests unchanged; old payloads validate |
| 1 | Control plane core, fake adapter, tokens, evidence, receipts, reconciler | Fake-mode unit/integration lifecycle passes |
| 2 | Buyer graph/client/proxy, orchestrator secret-ref wiring, registered Verifund A2A agent, CopilotKit chat workflow, Transaction Room | Fake-mode chat and browser E2E pass |
| 3 | Seller token verification, evidence outbox, protocol fields | Seller cannot accept/order without valid hash/token/funding |
| 4 | Sandbox adapter, webhooks, Payouts, preflight | Manual sandbox smoke records real PayPal IDs |
| 5 | Docs, compose profile, demo scripts, release notes | Acceptance criteria pass |

**Rollback:** set `VERIFUND_MODE=off`, stop the control plane and Verifund A2A
agent, and redeploy buyer, orchestrator, and seller. New fields are optional;
old payloads work. No existing SQLite table is altered; only new tables are
created.

**Deployment order:** control plane → buyer → registry → Verifund A2A agent →
orchestrator → seller → console. Buyer and seller deploy together because both
models use `extra="forbid"`; the optional fields make a brief skew safe.

## 17. Acceptance criteria

**Functional**

- Fake-mode E2E completes award → Verifund agreement draft/canonicalization →
  buyer agent review → seller agent acceptance → human funding approval → funding →
  PO → evidence → verification → release → payout →
  receipt.
- Buyer-agent and Seller-agent decisions are both persisted against the same
  agreement version/hash; either rejection blocks human funding approval.
- Changed/counterproposed terms create a new agreement version/hash and require
  both remote agents to review that version again.
- Chat HITL presents the exact agreement/hash before checkout and a separate
  release decision after deterministic evidence verification; no approval is
  inferred from free-form text.
- The Verifund Agent Card is discoverable independently of seller catalog
  discovery and supports structured status, evidence, funding, release, and
  receipt tasks.
- Chat checkout handoff opens fake checkout or the hosted PayPal payer-action
  page; chat reports funding and payout only after the buyer projection confirms
  them.
- Seller rejection moves `AWARDED` to `CANCELED` with a recorded reason and no
  ledger impact; buyer rejection does the same before capture.
- Sandbox smoke completes the same flow with real PayPal Sandbox order, capture,
  webhook, polling, and payout IDs.
- Console Transaction Room shows every state, deadline, evidence item, payout
  status, rejection reason, and a verified receipt.
- `off` mode preserves the existing MarketMesh flow, tests, and demo.

**Money and integrity**

- Agreement hash binds acceptance/rejection, approval, PO, seller token, and
  release.
- Tampered hash, amount, seller, or transaction ID returns `409` and moves no
  money.
- Ledger balances after release; no duplicate capture or payout.
- Receipt payload hash and HMAC verify; `kid` is present.
- Payout retryable failures stay `PAYOUT_PENDING`; terminal failures become
  `FAILED`; returned/reversed funds become `REVIEW_REQUIRED`.

**Security**

- Ops endpoints reject missing/wrong tokens; seller tokens are
  transaction/scope/hash-bound and expire.
- Seller cannot read another transaction or buyer-only data.
- Ops and seller tokens never reach the browser, trace, logs, console bundle,
  orchestrator LLM context, or AG-UI state.
- The Verifund A2A service's internal credential stays server-side; it receives
  neither `VERIFUND_OPS_TOKEN` nor PayPal credentials.
- Evidence upload rejects path traversal, oversized files, and unsupported MIME
  types.
- Sandbox mode rejects default secrets and live PayPal hosts.

**Resilience**

- Duplicate webhooks are idempotent; out-of-order and unknown events are stored
  and reconciled.
- Crash between provider call and DB write recovers without duplicate
  capture/payout.
- Funding and payout polling work without webhooks.
- Evidence deadline and inspection window produce the documented
  `REVIEW_REQUIRED` behavior.
- SQLite busy returns `503` with retry guidance; no multi-worker control plane.

**Console and docs**

- No demo escrow copy remains; sidebar label is transaction-oriented.
- `review_required` is paused, not terminal, and polling slows rather than
  stops.
- Seller dashboard shows settlement/evidence status without exposing tokens.
- PayPal Sandbox setup, env vars, demo commands, and troubleshooting are
  documented.

## 18. Risks and mitigations

| Risk | Mitigation |
|---|---|
| A2A 60-second timeout blocks settlement | Funding/release are LangGraph interrupts; no long provider wait inside an A2A call |
| SQLite write contention | WAL, `busy_timeout=5000`, single control-plane process, `version` guards |
| Webhook tunnel unavailable | Polling fallback plus reconciler; portal links remain signed |
| Duplicate capture/payout after crash | Provider intent rows plus stable idempotency IDs |
| Contract `extra="forbid"` breaks mixed versions | Optional/defaulted fields; deploy buyer/seller together |
| Token leakage through traces or AG-UI state | Seller token in buyer/seller secret tables, not graph state; secret-ref resolution; redaction |
| Orchestrator sees the seller token | Secret ref only in LLM/AG-UI; token resolved at send time; redacted from tool traces/logs |
| Fake and Sandbox behavior diverge | Shared capture/payout services; adapter only translates HTTP |
| PayPal account setup is incomplete | Preflight script plus documented checklist |
| Evidence storage grows unbounded | Size limit, content addressing, retention policy deferred |
| Receipt key rotation breaks verification | `VERIFUND_RECEIPT_KEYS` map plus `kid`; old keys retained |
| Console stage proliferation | Shared `lib/stages.ts` and a typed projection |
| Reviewer override abuses release | Override requires captured funds, a note, and an audit entry |
